# Package ZYND as a Public ChatGPT/Codex Plugin

## Goal and decisions

Ship one public, installable ZYND plugin consisting of the existing authenticated `https://api.zynd.ai/mcp` server plus packaged memory/context/card skills. ChatGPT/Codex can read private context, propose memory writes, and review/publish explicitly confirmed card facts. No new MCP tools or UI are required. Use the existing MCP tool groups `memory:write`, `cards:read`, `cards:approve`; exclude `people:message`, legacy `user`, and unrelated integrations from this plugin's granted tool list. Other MCP clients and the old ChatGPT Action remain unchanged.

- Context reads only when relevant to the user's request, not at every chat start. Proactively offer to capture durable facts, but call `report_user_info` only after explicit user approval; never infer/save secrets or sensitive facts without consent.
- Request all three plugin scopes on initial OAuth connection, visibly disclose private read/write and potential public card publication. For each `approve_fact`, require a separate explicit user confirmation tied to the exact pending fact. Denial, expired/revoked credentials, or missing scope must never publish.
- Use a stable, dedicated public PKCE OAuth client ID registered for the plugin (not the existing confidential ChatGPT Action client and not a client-name/DCR-label heuristic), with the existing ZYND login, the same `/mcp` resource URL, exact registered callback, and token/refresh binding. Do not put tokens or secrets in the plugin ZIP.
- Public directory submission is an external, human-owned step. No live deploy, DNS/provider setting change, secret rotation, or database migration is authorized by this plan; auth changes and any prod operation require human approval under `AGENTS.md` section 6.

## Existing evidence and caveat

`services/memory/app/mcp_http.py` already hosts `/mcp`, serves three `skill://` resources, and installs `ScopeGate`; `app/services/mcp_scopes.py` defines the three relevant groups. `app/mcp_owner.py` checks `cards:approve` and `confirm=true` for approvals. However, current public OAuth (`app/oauth.py`) normalizes connector requests to `user`, records `user` grants, and `app/auth.py` issues `scp:["user"]`; its discovery advertises only `user`/`ingest`/`offline_access`. Therefore a ZIP alone would make the plugin see every tool. `skill://` resource listing is not the same as an OpenAI native packaged skill or a supported `skills/list` import. The auth and web files are concurrently modified in the worktree: read the latest state/diff and coordinate before editing; do not undo unrelated changes.

## Ordered implementation

1. Recheck current `services/memory` tree, deployment status, baseline tests, and the official [package](https://developers.openai.com/plugins/build/plugins), [skills](https://developers.openai.com/plugins/build/skills), [auth](https://developers.openai.com/plugins/build/auth), and [submission](https://developers.openai.com/plugins/deploy/submission) requirements. Pin actual production `/mcp` URL and verify discovery/routing before treating the package as deployable. Read stack-specific instructions if present. Do not assume monorepo memory code is live.
2. Implement a dedicated plugin public client in `app/oauth.py`, `app/auth.py`, and relevant config/consent UI, without routing it through the legacy confidential ChatGPT Action logic. Register a stable client ID with PKCE S256 and exact callback validation; reject unregistered callbacks and client impersonation (DCR/CIMD must not claim the reserved ID). Accept only `memory:write cards:read cards:approve` for that client; preserve ordinary connectors' existing `user` behavior. Advertise these scopes consistently in authorization-server and MCP protected-resource metadata. Require explicit consent showing private memory access, memory writes, and card publication. Bind client ID, scopes, resource, redirect, code challenge, connection identity, and subject through code exchange, rotating refresh, revocation, JWT `scp`, and token response; refuse scope escalation on refresh. Keep legacy grants and deployments compatible. If existing authorization data requires schema changes, pause for human approval and follow `packages/db/README.md` rather than writing ad hoc SQL.
3. Keep `ScopeGate` as server-side authorization for listing **and calling** tools. Validate with a plugin token that the visible set is exactly `MEMORY_TOOLS | CARDS_READ_TOOLS | CARDS_APPROVE_TOOLS` (including existing `list_intros`, `set_looking_for`, and `update_headline` placeholder); `people:message`, exports, social tools, publishing pages, and third-party integrations must be absent and uncallable. Review all included tool descriptions, titles, annotations, and result schemas against actual behavior; do not claim `update_headline` edits a card. Mark externally visible approval appropriately and retain server-side `confirm=true`; for stronger per-fact assurance, validate a confirmation bound to the exact pending predicate/object rather than treating a model-supplied boolean alone as proof of human consent. Do not weaken other clients' behavior.
4. Add a portable plugin folder (e.g. `plugins/zynd/`) with root `plugin.json` using `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`, and `mcp.json` using its MCP schema, `type: "streamable-http"`, the existing HTTPS `/mcp` URL, and `extensions.com.openai.auth` set to `oauth` with `client.mode: "provided"`, the dedicated public client ID, `tokenEndpointAuthMethod: "none"`, and the three base scopes. Include the existing three skills under plugin-root `skills/` as a single maintained source or reproducible synchronized copies; OpenAI-specific listing and review metadata go under `plugin.json` `extensions.com.openai`. Prefer this ZIP layout to a new `skills/list` server extension, because only ordinary `skill://` resources are currently implemented. Add an optional onboarding skill only if testing shows installation/auth requires guidance. No hooks, `.app.json`, or optional widget UI for this release.
5. Adapt packaged `zynd-memory`, `zynd-context`, and `zynd-card` skills to the chosen policies: on-demand recall, propose-then-confirm memory writes, exact-match corrections, pending-fact review, explicit per-fact approval before publication, and truthful handling of absent/disabled tools and failed writes. Remove prompts for unrelated networking/LinkedIn and blanket start-of-chat fetch. Keep package skills aligned with server skills when shared; do not inadvertently change Claude behavior without reviewing it. Add test coverage checking that bundled instructions reference only visible tools and that install-time skill activation is not confused with runtime MCP resources.
6. Prepare truthful public listing metadata: verified ZYND publisher, display name and concise capability descriptions, HTTPS website/support/privacy/terms URLs, licensed square logo/composer icon files, starter prompts, permitted country availability, and release notes. Include five positive and three negative realistic review cases (private context read, approved memory save, pending fact review, confirmed publish, rejected/absent fact; unauthorized/sensitive save and unconfirmed publish among negative cases). Provide a dedicated non-production-data review account with representative private/public facts and card permissions, plus reviewer sign-in instructions and a walkthrough recording URL **outside** the ZIP. Do not include account passwords or tokens in repo or ZIP. Submit a complete ZIP with both MCP and skills initially; subsequent skill/metadata changes require a new package upload.
7. Before public submission, verify OpenAI organization ownership/identity, domain ownership, OAuth callback required by the portal, and the exact `.well-known/openai-apps-challenge` URL. Any DNS, provider allowlist, production deploy, or dashboard setting change is a human-approved operation. Connect the draft with OAuth in the portal, scan the discovered tools, resolve tool/skill/metadata issues, test private install in a fresh ChatGPT and Codex session, then hand the reviewed ZIP and review materials to a human for submission and publication. No assumption that installing a plugin automatically loads context in every unrelated chat.

## Validation and rollout

- Run `services/memory` baseline and post-change `uv run pytest -q -m "not integration"`; report only new failures versus repo baseline. Add focused tests for client classification, discovery, PKCE/callback, consent, scope grant and refresh persistence, cross-client scope escalation, revocation, list/call filtering, confirmation/rejection, and compatibility of normal connector and old Action flows. Test against isolated Postgres/Redis and fixture accounts, not shared prod data.
- Validate packaged JSON against published schemas, safe relative paths and image assets, and inspect the ZIP for secrets. Test MCP Inspector and OpenAI draft scan with a plugin account; assert only expected tools appear. Exercise direct, indirect, and negative prompts in real ChatGPT/Codex, including private-read leakage, repeated unconfirmed `approve_fact`, and prompt-injection attempts to invoke hidden integrations. Record any surface not verified as such.
- After explicit approval, roll out memory auth changes before submitting the plugin ZIP. Because the same `/mcp` serves existing clients, test old full-`user` connectors and current personal-token clients before and after rollout. If auth or tool scan fails, stop submission/revert only the new plugin-specific behavior through a reviewed deployment; never revoke existing clients or delete user data as a rollback shortcut. Publish only after portal review and human approval; monitor failed OAuth and plugin tool calls without logging private facts or tokens.
